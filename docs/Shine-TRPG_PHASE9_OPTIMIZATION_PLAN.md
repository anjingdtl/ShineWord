## 1. 问题定义（诊断结论摘要）

| 根因 | 一句话 | 关键证据 |
|---|---|---|
| ① 供给节奏×密度 | 下一阶段局面只在当前阶段完成后才开始生成（反应式触发，无流水线）；阶段内容可直通闭合（1-4 回合关闭一阶段）；历史产率 2-7 有效决定/旅程 vs 配额 20 | replanService.ts:36-80；真实库 19 空转全落重规划窗口；n2 gmBrief"普通成功即完成" |
| ② 预算算术 | 每回合恒 2 请求；80 决定最少 148+重规划 18+开局 5≈171；A1 裁决后可行（余量 9%），否则 ~250 不可能 | v2Turn.ts:420；manifest 1291/1500 |
| ③ 长规划肥尾 | 单发 25-45K token、实测 545-822s，J2/J3 在 900s 时限时 0 业务字符（推理 >37K token 满速未收敛）；wire 上限 49762÷45tok/s≈1106s 永远装不进 900s | stream bin 逐帧统计；requestDeadline.ts:20 |

放大因素：旧驱动通用 fallback 烧 38 请求（19 空转×2）；通用开局零效果定义被当推进路径；J1 两后果 effectSpecs 仅 record_event 且方法门槛排除 committed_event（后果机械上无法改变可用方法）；post-processing 旧卡租约阻 J1 导出（可正式回收）。

**本方案的 fun hypothesis 等价物**（这段旅程为什么能玩）：玩家在每个阶段都面对"准备→兑现"的真实因果链，每个决定都能在下下个决定之后还听到回响；系统永远有下一张可打的牌，玩家永远不会被迫在空房间里原地转圈。

设计支柱（之后每个改造项用这三条过审）：
1. **不断供**：阶段完成的瞬间，下一阶段内容已 ready 或在稳定边界等待采用——玩家侧零真空。
2. **可消费**：每个后果必须长出牙齿（relationship_shift/grant_knowledge/promise_create），被下游方法门槛或节点条件实际引用；record_event 只作旁白不作效果。
3. **可交付**：任何一次模型调用在其时限内有 ≥95% 的完成把握；完不成的调用在派发前就不该被派出去。

## 3. 改造项详设

### P9-O1 流水线预生成（核心，对应诊断 A2）

- **purpose**：消除根因①的节奏断供；实现方案 §7"阶段切换前提前准备依赖"的原意。
- **玩家体验目标**：完成一个阶段后，"后续方向待准备"的空窗不再以几十分钟计；玩家永远有有意义的下一步。
- **inputs**：当前 plan revision、runtime nodeStates、已提交事实（actors/items/discoveries/relationships/situations）、provisional 后继节点列表。
- **机制**：
  1. 触发：在 `evaluateReplanTriggers`（replanService.ts）之外新增前瞻判定挂点（建议与 settleCampaignProgress 提交后同处评估）：当前 primary `status='active'` 且其局面未解决，且下一主节点 `coverage='provisional'` 或无可用局面 → 以 `triggerReason='stage_content_prepared_ahead'` 入队 replan 任务（`enqueueReplan` 复用，单飞合并不变）。
  2. 生成：复用 `runCandidateJob`；材料=当前计划+已提交事实；提示合同要求只为该后继节点产出局面定义，provisional 更远节点照旧不展开。
  3. 采用：复用 `adoptReplanCandidate` 稳定边界 CAS；玩家有在途回合时候选只落 candidate_ready，在下一管理边界采用（§10.3 不变）。
- **outputs**：后继节点 `situationRef` 落地、coverage provisional→concrete 的 plan revision+1 与对应 artifact。
- **edge cases**：①预生成期间当前阶段被玩家提前完成→候选按既有 stale/事实校验处理；②意图变更→intentHash fence 使候选 stale；③多个 provisional 后继→一次只预生成最近一个，不发散。
- **failure states**：预生成 invalid/unknown 不阻塞当前玩法，原因入诊断；同一节点预生成失败 ≥2 次→停止自动重试，公开"后续内容准备失败"状态，等待玩家显式操作（有界，不无限付费）。
- **不做什么**：不预生成结局、不提前实例化人物、不消耗玩家资源、不产生玩家可见剧透。

### P9-O2 流式活动心跳超时（止血，对应诊断 A3）

- **purpose**：根因③的传输层止血；在 P9-O3 未落地前把 J2/J3 类样本从"900s 必死"变为"活着就能跑完"。
- **机制**：流式请求的超时从"绝对 900s"改为"活动心跳"——每收到一个 SSE 帧即重置计时；连续 60s 无帧判 network_unknown；绝对硬上限 1200s（high 档，现成配置档）。60s [PLACEHOLDER·验证路径：GLM 流实测帧间隔 ≈38 帧/s，单帧停顿理论上限未知；若真实样本出现长静默思考期，上调至 120s 并记录依据]。
- **edge cases**：缓冲（非流式）请求维持绝对时限不变；unknown 语义不变（禁止自动重发）。
- **failure states**：1200s 硬上限到达仍 unknown→按既有正式清扫流程，不自动重发。
- **正确性代价说明**：该改动承认"只要模型还在产出，等待就是有效的"。它不解决推理量肥尾本身（那是 P9-O3 的问题），只消除"时限坐在分布尾部内侧"的系统性误杀。

### P9-O3 分阶段有界生成（正式设计变更提案，对应诊断 B1）

- **地位**：这是对"一次 campaign_plan 请求同时产生全部内容"（§6.2）的**设计变更提案**。启动条件：P9-O2 落地后 J2/J3 任一仍触硬上限 unknown，即启动；否则后置到预算结算点之后再议。
- **purpose**：把肥尾分布（25-45K token、500-1300s）切成三段细尾分布（各 ≤20K token、300-500s），每段在其时限内有 ≥95% 完成把握；中间产物不可变、可恢复，单段失败不报废整计划。
- **机制**：
  | 段 | 产物 | 规模上限 | 目标时长 | 说明 |
  |---|---|---:|---:|---|
  | S-A | proposal + stages 骨架 + endings | wire ≤ 20K token | 300-500s | 含节点图/条件/结局引用；本地校验图可达与结局引用闭包 |
  | S-B | firstSituation 完整四档 | wire ≤ 20K token | 300-500s | 输入=S-A 冻结产物；本地校验效果生产者→completion 消费者闭包 |
  | S-C | consequences + rewards + clues | wire ≤ 20K token | 300-500s | 输入=S-A+S-B 冻结产物；本地校验 schedule_consequence 引用闭包与可消费效果 |
  每段独立落盘（durable artifact）、独立恢复、跨段一致性由本地校验完成（模型不自验证跨段）。
- **数值 rationale**：rev3 实测正文 14,416 字符 ≈ 5-6K token；推理量为正文 3-5 倍 → 单段 ≤20K token ÷ ~45 tok/s ≈ 445s，对 900s 时限留 2 倍余量。
- **edge cases**：S-B 失败重试只重发 S-B；S-A 变更使 S-B/S-C stale；修复轮计入对应段的两请求上限。
- **failure states**：任一段两次请求仍 invalid → 整计划 invalid，保留各段原文；unknown 不自动重发。
- **迁移影响**：冻结根增加分段产物引用；恢复点按段登记；预算合同从"每计划 ≤2 请求"改为"每段 ≤2、每计划 ≤6"——**每计划成本 1-2→3-6 请求，需与配额节奏重排预算**；旧冻结任务不按新合同恢复。

### P9-O4 后果消费审查项（对应诊断 A5，不新增硬门）

- **purpose**：根因①消费链的验收侧修复；遵守 final18 原则（审查项，非硬门）。
- **机制**：CONTENT_QUALITY 六维之"后果持续"评分具体化为三子项，全满足才记 ≥3：
  1. effectSpecs 含至少一种可消费效果（relationship_shift / grant_knowledge / promise_create / situation_counter）——record_event 单独出现记 0；
  2. 存在引用该效果的下游方法门槛或节点完成条件（promise_fulfill / knowledge_known / relationship_at_least / counter_at_least / committed_event 仅限节点条件）；
  3. 排程与触发之间 ≥2 个有效决定（审计工具既有字段）。
- **生成提示侧**：在既有后果规则后追加一句消费导向说明（"后果的效果应能被后续办法或阶段条件实际消费；纯 record_event 后果不计入持续后果"）。提示追加仅一句，不堆规则（诊断根因③：每条规则都在拉长推理）。

### P9-O5 驱动纪律修正（QA 资产，对应诊断 A4）

- **机制**：r67-drive 的停止条件从"零变化即停"改为：**非失败档连续两次零持久变化才停**；失败档（failure/severe_failure）零效果是合法玩法，单次即继续，但连续 3 次失败档仍停（防刷失败）。其余不变：只选 camp-sit-* 方法、单派发、逐次审计、无战役方法且有合格 replan 候选时才 replan。

### P9-O6 post-processing 旧卡正式清扫（操作，对应诊断 S1）

- **机制**：导出前走正式 `session.resumePostProcessing(branchId)`（turnPostProcessing.ts:185 可回收过期租约）；清扫完成以 `frozen_turn_postprocess_outbox` 无 running/blocked 为准；J1 主分支导出解锁。**禁止手改 outbox/lease/数据库。**
