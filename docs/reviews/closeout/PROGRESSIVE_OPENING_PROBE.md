## 实验与结果

- `npm run build:core`：通过，仅生成被忽略的编译产物。
- 小说：用户提供的《白篱梦》，3,065,535 bytes，965,458码点，300章。
- 当前默认全量计划：15组，最大组68,719码点。
- 有界输入：开篇最多12,000码点，实际含11段、11,999码点（未包含段落切分空隙）。
- 使用当前`LlmGroupExtractor`与`OpenAICompatibleProvider`，追加约束：最多12实体、20事实、6事件，不生成ruleMappings，不宣称全书覆盖。
- 配置来源：用户指定的`GLM-TEST.txt`；模型标识`GLM-5.3-Flash`；保留现有推理开启政策，不输出密钥或端点。
- 本地解析：103ms；模型尝试：1次物理请求。
- **请求约90,010ms后超时；总探针90,114ms；没有获得可用模型结果。**
- 未保存正文、回复或推理内容；没有可用usage、HTTP完成状态或首token计时。

## 解释边界

该结果不支持“一次小请求已经能快速开局”的结论，也不能单凭超时区分网络、服务排队、模型生成或网关问题。非流式路径没有完成，未独立记录响应头和首token，不能声称模型90秒完全没有生成。

新路线将首开模型源文从近百万码点减少到约1.2万码点，属于输入工作量下降，不代表同比80倍速度提升。需要进一步测量小schema、不同输入长度和真实可用模型，完成开局包编译及App首回合后再评估TTFP。

用户明确要求只交付MD方案及提示词，因此临时探针脚本已删除，产品源码未修改。该失败实验如实保留，不重试完整长任务。

## 给施工Agent的复现约束

1. 在隔离工作目录写有界harness，复用当前Provider，进程内读取用户配置，不打印key/原文/响应body。
2. 先运行微小JSON基线，再选1k、4k、12k原文；记录全部物理请求和timeout，单次≤90秒、整组设总预算，达到预算停下并报告。
3. 原文按真实分章与码点范围构造segments；记录数量、大小、耗时与结构结果，不输出小说。
4. 捕获并脱敏分类网络错误、HTTP状态、响应头耗时、可用token时刻、finish_reason和usage；不可把未知阶段武断归为推理慢。
5. 得到结果后检查引用定位、字段语义和开局编译；单次成功仅是可行性，不作为P95或稳定性能证明。
