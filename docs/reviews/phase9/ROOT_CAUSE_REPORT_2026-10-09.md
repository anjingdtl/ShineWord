# Phase 9 长期未全 PASS 的根因与处置（R67–R68）

结论：主要瓶颈已经从执行引擎的正确性转为**真实生成内容能否形成可持续的玩法**；同时，旅程计量和分叉历史交接的缺陷掩盖了这个瓶颈。继续增加回归测试数量、重复点击或追加提示词，都不能证明内容验收通过。本批修复有确定反例的共用工程路径；内容缺口如实保留，不补造剧情、骰点、效果或配额。

证据根目录：`.tmp/phase9/local-20261009/`。最终源码 scope v3：`c55f8a198bc69b9e54b651ec93fdc07916ccfeb4d14f347ec54ee9b26876d0b4`；APK：`041fff2a110faec7fc3c0e2ccf3937cd53b9041e42c55ce72341e7eba9483420`，109788983 bytes。完整核心1193/1193、移动类型/版本/Debug构建通过；API35保留数据安装 hash 一致。当前40项证据及每项残余见 [当前身份报告](CURRENT_IDENTITY_R67_2026-10-09.md)。整体仍未通过。

## 1. 首要根因：能执行合格内容，不等于能稳定生成合格玩法

`compileOpeningSituation.ts` 是保守的本地开局编译器：survey、ask-around、get-moving 有文字、技能与第一步，却没有 successEffects、onSuccess/onFailure、outcomeTemplates，transitions 为空。真实合同四档的状态效果也为空。**没有丢失的 counter/completion 事件可供引擎补回。** 通用方法可以消耗时间并获得叙事，但无法自动变成调查、承诺、阶段解决或后续机会。

接手v25的26条Committed记录实际是24条玩家提交和2条管理提交；24条中19条是这种通用空转，仅5条有状态变化候选。turn-0002只有重复街谈和standing增加，其语义有效性还需审查。证据：`r67-content-diagnostic.json`、`r67-turn-diagnostic.json`、`r67-j1-corrected-audit.json`。这是 final18 类型的内容定义缺口，不能以“每次成功加一”或硬性要求所有失败有变化来修复。

本批正式重规划后，rev3的n3已有整理见闻、旁听收集、递呈陈情三个具体方法，并有准备条件。turn-0027的automatic成功确实产生知识、counter和新业务事实；turn-0028失败无持久变化。J1到v28为26条玩家提交、6条有效候选、20条排除。**失败一次并不能证明后续路径不可达**；也不能用重复失败或counter刷取补20决定。本批没有把这个局部成功宣称为完整玩法修复。

根本解决应在内容创作和独立审查中证明完整因果链：已有事实→不同准备/行动→普通成功可达的阶段解决→两个持续后果→以后人物态度/可用方法/代价的实际用途。检查应同时追踪效果生产者和后续条件消费者，并用真实普通成功、失败后继续和跨节点实例验证。生成提示已写有普通成功、准备、反重复等规则，继续堆提示不能替代这条证据链。按既有合同，不新增内容硬门，不改已采用档案。

## 2. 计量根因：把提交与版本增长当作有效决定

旧驱动以committed加一，有可用通用方法就继续；固定1000分的优先级加上不断增长的最近使用分数，也不能永久保证战役方法优先。它还包含最多三次的宽泛step重试，无法从脚本本身保证未知结果绝不重发。未证明发生重发的样本不凭推断定罪，但该脚本不再作为本批续跑入口。

审计工具原先混入采用记录，识别recordEvent外层类型而非payload中的业务事件，增量窗口又裁掉后果间隔所需历史。本批三个RED反例后修复共用审计工具，候选计数仍须语义审查。新驱动仅选择当前战役方法、派发一次、逐次审计；无效果/未知/缺具体方法时留下证据并停止诊断。QA step在关闭SQLite前等待正式post-processing工作交接，避免先关数据库把memory租约留成running。

**撤回A19的“已证1/2”：** consequence-visit-introduced在v4排程、v19触发，但中间有效候选决定为0。“跨15个版本”不等于“隔两次有效决定”；其record_event文案也不能单独证明以后的牢中交涉更顺利。当前合格的两项延迟用途仍未证成。

证据：`r67-audit-red.log`、`r67-audit-green.log`、`r67-J1R66-driver.jsonl`、`r67-memory-diagnostic.json`、`r67-j1-export.log`。既有running memory工作仍需通过正式恢复接口处理；没有手改outbox状态解除导出门。

## 3. 工程根因：分叉复制了合同，却没有复制完整的合同依据

真实J4分叉导出失败，错误为“Frozen contract content binding has no matching historical snapshot”。原分叉复制所有截至分叉点的Committed回合，却只保留头部快照。补齐游戏快照后，真实导出仍失败，暴露第二层：渐进建设可在**同一游戏状态版本**发布多个不可变内容版本；旧快照中的内容清单不一定是下一回合冻结时采用的清单。

真实turn-0004的expected v3冻结了content v1，而已提交v3快照仍指向基础content v0；父分支有(v3,v0)与(v3,v1)两代清单。只复制快照内的清单，会把后生成的那一代丢掉。类似问题还存在于v4/v5。证据：`r68-binding-diagnostic.json`；最初失败的J4AR67、J4AR68分支和导出日志均保留。

R68修复 `forkBranch` 共用路径：在同一事务中复制分叉点及之前的完整游戏快照和**全部内容代次**，只重绑定目标分支标识；已付费合同、骰点、原分支历史逐字节保持，分叉点之后的未来不复制。新反例覆盖历史导出/恢复再导出、历史写入失败整笔回滚、同一游戏版本在冻结前新增内容代次。

RED见 `r68-red-c.log`、`r68-generation-red-b.log`；修复后 `r68-generation-green.log` 3/3。真实同v26的J4AR68C/J4BR68C分别成功导出1017323 bytes存档（`r68-final-j4-fork-proof.json`）。新APK通过Android正式文件选择器导入A存档为 `camp-mv0mwyt5-main`，继续入口正确显示v26目标和三个准备/行动方法；见 `r68-device-import-result.xml`、`r68-device-ready.xml`、`r68-device-audit.json`。这是原失败路径的实证修复，不等于A/B各10决定或Android30决定已完成。

## 4. 规划可交付性：流式解决300秒网关，不保证900秒内完整交付

J1本批正式重规划一次完成，约702.081s；J2/J3新规划均收到200流式响应头，却在900.037s/900.027s达到既定时限，进入outcome_unknown，没有可独立六维审查的完整候选。请求wire上限49762是预算上限，不是实际生成token数，不能据此断言超时的唯一原因。证据：`journey-http.jsonl`、`r67-j2-plan.log`、`r67-j3-plan.log`及原始stream记录。

已确认的事实是：完整长计划的端到端交付仍不稳定，R66的流式修复只消除了另一种传输失败。本批没有把流式首包、部分JSON或模型自评当ready，也没有重发两个未知规划。解决方向需要在**新的正式任务/配置**中验证有界创作阶段、可恢复的不可变中间产物和实测交付预算；不得偷偷改变旧run的传输方式、延长旧冻结配置或裁掉意图。仅把timeout再加长也不足以证明解决了根因。
