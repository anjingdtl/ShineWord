## 3. 必须关闭的缺陷

### R2-01 [P1] 战斗权威状态没有统一原子提交

依据：`src/application/campaign/encounterService.ts::applyAction` 先调用 commitResolvedTurn，随后另行 persist 遭遇；persist 又在 saveEncounter 后单独更新 distance_bands_json；cleanupHostiles 是另一事务。

复现故障点放在主回合提交后的第一个遭遇持久化入口，抛出可恢复的存储错误。伤害与版本已成功写入，游标没有前进，证明中断会形成部分提交。并非仅 UI 显示延迟。

begin 也将敌人插入与遭遇保存拆开；移动、passTurn、retreat 则直接持久化遭遇或清理演员，不经完整回合版本。这些路径都属于同一根因，不能只修一次攻击。

关闭标准：引入统一的战斗 Action/UnitOfWork，将开始、移动、攻击、AI 动作、援救、戒备、撤退、结束、战利品、临时演员清理、行动游标、时钟、事件、快照纳入一致事务。冻结合同/骰点仍预先持久化。提交失败、提交后 UI 崩溃、重复请求都能恢复，且没有双扣资源、双次行动或同一投骰被套用到不同动作。

对应原方案 §12、§13.1、§13.3、§15.2；不是新增验收要求。

### R2-02 [P1] 战斗历史与存档不完整

依据：`domain/state/types.ts` 快照含 actors/skills/relationships/cards/party，但没有 encounter 状态；`application/branch/fork.ts`、`application/export/saveFile.ts` 没有完整导出/恢复 encounters 与战场信封。

在完成一次真实引擎攻击后，分叉与存档往返都保留敌对卡片，但没有活动遭遇。由此可能在敌人仍存在的情况下跳出战斗，且无法按历史继续先攻。

关闭标准：完整快照/事件覆盖遭遇 ID、状态、参与者、先攻、游标、轮数、区域图、各角色区域、移动/主要行动额度、必要触发效果与待执行动作。分叉、导出、干净库导入共用同一恢复契约。所有 branch/campaign 引用正确重映射；结束后的存档不能再次恢复临时敌人。

必须验证战斗前、开始后未行动、移动后、已投骰未提交、已伤害提交、援救后、撤退/结束后等检查点。只在退出战斗后往返成功，不算战斗中存档通过。

对应原方案 §15.2、§16、§19。

### R2-03 [P1] 标准移动与跳过没有完整行动额度/时钟约束

依据：`EncounterService.playerMove` 只校验相邻区域，然后直接修改 zoneMap；没有每轮移动额度。passTurn 单独推进 initiative，没有通过正常时钟结算。

已动态复现一轮两次免费移动且版本不变。静态还可见当前轮时钟主要由攻击合同的 withRoundClock 处理，须检查轮末为跳过、援救、AI 移动/撤退及失能跳过时是否漏加/重复加 6 秒。

关闭标准：规则统一表达每轮 1 主要行动＋1 标准移动，疾行显式消耗主要行动；多次移动、边界行动、失能恢复、全部角色跳过、新加入参与者都有确定性行为。世界钟在完整轮结束时推进一次，与动作种类无关。

对应原方案 §10.3、§12.2。

## 4. 尚不能宣称全部关闭的范围

以下是源码/调用核查结论，不冒充设备动态测试：

1. **世界编辑与可移植世界包**：App 的“编辑模式”目前主要是完整资料阅读切换。未发现条目草稿编辑、差异预览、编辑后验证发布及 `.shineword-world.zip` 导入导出的完整操作链。存档 JSON UI 已接入，应保留其成果；它不等于世界包交付。对照 §14、§16、P2-5。
2. **发现与长期记忆接线**：BooksScreen 给玩家透镜固定传空 discoveredEntryIds，安全地隐藏了未发现内容，但没有把实际发现记录接入阅读视图。session 仅取最近 6 条、每条 120 字的叙事；长期事实/摘要检索仍未接入，不能把所有长期记忆要求改为“后续增强”。对照 §10.4、§14、§19。
3. **任务/知识与完整状态**：有相关类型/部分建表不等于事件驱动的任务、线索、知识传播与奖励闭环。须以至少一条实际任务链验证发现→知识→任务推进→奖励→回退/恢复，而不是只展示开局目标文字。对照 §10.4、§15.2、P2-3。
4. **能力资格检查**：v2Compile 已阻止自由数值注入，但能力编译仍需检查准备/冷却/射程、世界硬约束与目标政策。当前已习得或已准备满足其一即可进入使用路径，resolveAbilityTarget 对 self 直接返回外传 targetId；应在收尾时补负例，不能只以 HP 封顶代表全部资格成立。
5. **验收矩阵**：修复报告明确仅 GLM、未测真机/minSdk24、未交付签名 Release。实际可获得的环境应补测，缺失的外部条件如实列待验收；不将单次内存库往返或引擎长程代替所有 UI/设备/故障检查。

开发状态的“7 动态缺陷＋6 范围缺口全部关闭”应改为准确的逐项状态。上一轮 G 编号在新修复报告中重新分配，造成原范围不便追踪；收尾应以原报告编号＋原方案章节交叉核对，不能用更窄的新 G 项替换原缺口。
