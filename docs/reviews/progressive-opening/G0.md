## Endpoint probe

The bounded probe used the supplied GLM configuration and the supplied `《白篱梦》` TXT. It sent four physical streaming requests in order: tiny JSON, then the first 1,000, 4,000, and 12,000 Unicode code points. Each sample had one attempt, a 90-second request timeout, and a 360-second group deadline. Reasoning remained enabled; the request did not contain a thinking opt-out. The probe persisted only the redacted summary at `.tmp/progressive-opening-probe.json` (gitignored).

The tiny request established the route and JSON response. The three content samples did not produce a parseable dossier. The endpoint exposed no queue-duration header, so provider queue time is unknown. The first request's client network timings were local socket wait 17 ms, DNS 75 ms, TCP 1 ms, and TLS 1,406 ms. Subsequent requests reused the connection; their DNS/TCP/TLS phases were therefore not sampled separately.

One targeted follow-up tested whether a larger output cap was enough: a single 1k-code-point request with 2,048 output tokens. It completed in 47.72 seconds (HTTP 200; headers 1.20 s), used 911 prompt, 2,048 completion, and 2,009 reasoning tokens, returned zero text tokens, and ended with `length`. This is a failed extraction, not a successful opening.

Two bounded, app-shaped probes then compared the other model already reported usable in the supplied config. The probe accepted an explicit `--model` option; it did not change the app's saved profile or reasoning policy.

The successful repair shows a complete dossier is possible with this manually selected model and a larger output allowance. It consumed the full two-request ceiling and took 88.3 seconds for dossier extraction alone. That exceeds the 60-second median target before local compile, publish, character setup, or the first game turn. The 120-second P95 remains unmeasured; one successful probe is not a percentile. Provider queue time was not exposed, and there was no HTTP or safety error. Redacted per-attempt data is retained in `../closeout/PROGRESSIVE_OPENING_GLM53_PROBE.json` and `../closeout/PROGRESSIVE_OPENING_GLM53_8000_PROBE.json`.

Across the five current requests, provider transport returned HTTP 200 and exposed no safety-filter or network error. The failure was output truncation after reasoning consumed the configured completion budget. The older 90-second non-streaming 12k probe in `PROGRESSIVE_OPENING_PROBE.md` remains a separate observation: it timed out without response-stage data. The prior C3 sample in `FINAL_REPORT.md` completed in 30.7 seconds with a different prompt/input and reported 1,176 reasoning tokens within a 2,000-token completion; these runs are not equivalent workloads.

The evidence establishes one complete, citation-verified dossier with `glm-5.3` at an 8,000-token output cap, but not a playable opening or the 60-second TTFP target. It does not justify disabling reasoning or estimating long-request performance by scaling input length. A selectable `glm-5.3` profile with sufficient output allowance is the only tested successful option so far; the profile choice and the app's end-to-end compile/publish/first-turn latency still need verification.

## Code changes

- Added `scripts/progressive-opening-probe.cjs`, which reads the credential only in process and writes a redacted summary; source, prompt, key, endpoint, Authorization, reasoning body, and response body are not persisted.
- Added provider per-physical-attempt metrics with safe outcome categories, HTTP status, duration, reported usage, and available transport timings. Hidden reasoning retries can now be bounded explicitly without changing the reasoning policy.
- The fetch transport records response-header and complete-body timing. Fields it cannot observe (socket queue, first generated token, provider queue) remain null instead of being inferred.
- Successful world-build groups persist redacted request metrics alongside their existing unit usage data; failed attempts append metrics under the unit's fencing token and those metrics survive a later successful retry. Provider error messages are reduced to safe status/category text before they enter SQLite.
- Corrected the first retry delay: it previously used the pre-claim attempt count and could immediately repeat a failed first request with zero backoff. Failed physical-attempt metrics now append under the current fencing token and survive a later successful unit retry.
- Mobile extraction planning now derives context and output limits from the saved profile and caps the output reservation to the extractor's actual request cap.
- The run coordinator renews its fenced lease independently during long model calls, confirms ownership before accepting a returned extraction, and discards a response that arrives after user cancellation.

## Gate

G0 code and bounded endpoint observability are implemented. The endpoint's current constrained-output behavior blocks any honest claim that a complete 1–12k dossier is currently generated quickly. G1 must keep the physical-request cap, surface a recoverable preparation failure, and continue to use the existing publish validator. TTFP remains unverified until an actual complete dossier is compiled, published, and used to start the first playable turn.
