# Progressive opening G1: bounded dossier to published playable scope

Date: 2026-09-29 (Asia/Shanghai). The implementation was based on the live worktree at `d2f2336`, after the earlier review baseline `8eccb11`; user-owned planning files were left untouched.

## Implementation

- The library's default TXT path now stages and normalizes the source through the existing bounded streaming importer, then prepares only the first 8,000 code points for the opening dossier. It does not create or start the whole-novel extraction run. The old full-extraction code remains intact; the explicit full-refinement UI is still a G5 item.
- The dossier schema only accepts a current location, setting, immediate situation, first goal and unresolved questions. All four model evidence quotes must match verbatim inside the first 1,600 code points. The local compiler rechecks quote spans against the stored chapter and writes quote hashes and scope metadata. It does not persist the raw model response, prompt, key or full dossier response.
- The local compiler reuses the same baseline skills and GM guard template as the full package compiler, adds one opening lore entry and one playable scene, and publishes through the normal `publishWorldPackage` validator. The package is playable for the declared opening scope while explicitly marked partial for the full novel.
- New immutable packages use `world-package-3`. Their `buildScope` names the strategy, opening/incremental/whole-source scope, completeness, source code-point ranges and range hashes; that metadata participates in the content hash. SQLite migration 14 stores it outside `validation_json`, and portable package import/export preserves it. Existing v2 packages keep their version and existing content hash.
- Successful and failed opening requests persist only redacted physical-request metrics and safe result classifications. A failed request leaves the streamed source available for a retry. The library routes a successful publication directly to the existing original-character opening wizard.

## Live endpoint evidence

The probe used the authorized GLM key and the normalized 8,000-code-point opening excerpt from the supplied novel. It used the same model-facing system/user prompt and JSON schema as the app helper, retained the existing reasoning policy, and sent no thinking opt-out. Streaming was used only to observe first text timing; the production mobile transport remains buffered and cannot expose a first token.

| Requested output cap | HTTP / completion | Headers / first reasoning / first text | Usage and response | Physical requests |
|---:|---|---|---|---:|
| 4,096 | 200; 57.508 s complete | 1.619 s / 1.620 s / none | 6,014 input, 4,096 completion, 4,050 reasoning; `length`; zero business-text characters | 1 |
| 8,000 | Client timeout at 120.024 s after response headers | 1.204 s / 1.205 s / none | Usage unavailable at timeout; zero business-text characters; reasoning stream contained 12,326 characters | 1 |

Both requests reported no provider queue header. The 8k request did not trigger a JSON repair because it returned no business text. These results do not establish a successful dossier, opening publication or TTFP. Raising the saved output allowance to 8,000 was tested once and still timed out. No tested configuration currently supports the 60-second target; a different manually selected profile remains an unverified option and must pass a bounded complete-dossier probe before it is treated as a fix. Reasoning was not disabled.

## Follow-up: alternate model and Release attempt

The later bounded `glm-5.3` probe at an 8,000-token output cap returned a complete dossier after one repair: two physical requests, 88.281 seconds total, and all four source quotes matched exactly. This establishes endpoint feasibility for a dossier, not acceptable TTFP; extraction alone exceeded 60 seconds.

The signed v15 Release was then configured through the normal profile screen and used to import the supplied novel through Android's document picker. The app prepared the opening request for 8,000 code points, but reported a recoverable opening-preparation failure after roughly half a minute. It did not publish a package or enter character creation. The production-signed app does not permit `run-as`, so this run's locally stored safe metrics were not extracted from its database. No response, source text, key, or database was exported.

The G1 fixtures and full regression suite pass, but the real Release path has not reached package publication, character creation, or the first playable turn. TTFP remains unmeasured and the target remains unmet.
