# G4 review: immutable branch content and save lineage

**Stage:** implemented, reviewed, fixed, and regression-checked

**Date:** 2026-09-29 (Asia/Shanghai)

## Result

- Added migration 15 for append-only branch content manifest projections and immutable progressive delta packages. Existing world package revisions and their publish gate are unchanged.
- New campaigns bind an immutable base package. Branch reads hydrate the manifest for the requested state version; commits carry it into the next snapshot. Historical fork and rewind select the manifest that was active at the fork point and rebind only its branch/state coordinates.
- Frozen `ActionContract`s record the content manifest hash, version, locked base revision, delta ids, branch and expected state. The planner context is rejected before its request if its prepared content snapshot changed. Content published during a provider request remains unavailable to that frozen contract and is available on a subsequent turn.
- Progressive deltas are additive: entry ids cannot overwrite base or prior delta content, existing section titles cannot be silently changed, source ranges must fall within evidence already visible on that branch, and exact citations are checked against the active normalized source. Conflicts stay `needs_review`; they are not placed in an active manifest. Proposals cannot restore a branch-recorded dead NPC by reusing its template id or normalized name.
- The turn path may package exact, already-visible source excerpts with a local fixed template. It adds no interpretation, rules or unseen source text and makes no extra model request.
- Full saves use `shineword-save-6`, include each referenced published delta and state-specific manifest, and validate hashes before restore writes. Saves through v5 remain supported. World archives use v2 only when they carry branch content; v1 archives remain readable, and attaching a branch archive requires the matching published base hash, revision and target state.
- Progressive manifests are rebound for imported branch/world identities while immutable delta content hashes and origin lineage stay intact. No existing package, application id, key storage, rules, dice or growth behavior changed.

## Review fixes

- The first regression run correctly rejected a test delta whose range covered the whole source file. The fixture now derives its range from a player-visible citation and hashes that exact slice; arbitrary or future source ranges remain blocked.
- Hardened manifest, delta, save and archive shape checks so malformed nested JSON returns a validation error instead of throwing while dereferencing missing fields. `restoreSave` now requires the hash provider and validates the complete serialized save before opening its write transaction.
- Added a remapping regression showing the immutable delta is still loadable when the same base package is assigned a different local world id.

## Limits

- This stage establishes the immutable content and save lifecycle. Automatic preparation still only adds exact excerpts from source spans already cited as player-visible. It does not yet turn arbitrary unreviewed chapters into new factual rules or entries, and a miss does not mean the novel contains no answer.
- No Android device is connected. Device-specific migration, archive round-trip, lock-screen/background recovery and final Release APK behavior remain for G5 validation.

## Follow-up: user-confirmed source excerpts

The explicit book lookup adds one constrained delta path: a selected book may receive only a fixed-template, exact `lore` quote with one verified source range. It cannot publish a rule, public entry, summary, or inferred fact. The delta is immutable and bound to the current branch/state manifest; the quote remains hidden until a user-confirmed discovery lifecycle commit.

Regression covers unscoped ordinary publication rejection, unsafe-purpose rejection, delayed cancellation, duplicate lookup, hidden-quote projection/Planner filtering, knowledge confirmation, save validation, and rewind behavior. The complete suite passes 224/224. A production Release upgraded on the existing `Medium_Phone` AVD with `adb install -r`; its previous library/job records remained visible. This verifies the observed upgrade path without clearing app data, but does not replace a full on-device save/archive workflow.
