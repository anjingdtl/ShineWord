# Shine-TRPG 快速开局与渐进式三宝书建设方案

> 日期：2026-09-28；审查基线：`8eccb11`。  
> 用户已选择：**快速开局，三宝书随探索补齐**。  
> 状态：技术路线已明确；本次仅交付文档，未修改产品代码。有界模型探针不等于产品实现完成。  
> 优先级：取代上一轮收尾方案中“默认全书抽取、全量映射后才能开局”的产品门槛。旧版全量审计模式仍保留，数据完整性、证据、确定性规则和存档保护不取消。

## 1. 需要改变的是开局所需工作量

用户反馈《白篱梦》构建约两小时。手机游玩的首要指标应是 **导入到首次可操作回合的时间（TTFP）**，不是后台完成整本知识整理的时间。

上一轮方案主要解决错误哈希、导入内存、恢复和进度，却继续要求模型读完近百万码点、逐批抽取事实再映射，才允许游玩。这个前提不适合交互式手机产品，本次明确替换。

新默认流程：

```text
TXT → 本地分章/原文索引 → 有界开局资料 → 本地编译三宝书开局版 → 开始游玩
                             ↓
                当前地点/角色/事件驱动的按需检索与扩充
                             ↓
                  校验、缓存、版本锁定、逐步丰富三宝书
```

三宝书从“全书百科预编译产物”变为“有证据、版本化、按探索解锁的游戏资料视图”。未构建、未发现、未知是三个不同状态。

## 2. 当前代码与证据

| 观察 | 当前证据 | 判断 |
|---|---|---|
| 源文规模 | 3,065,535 bytes、965,458码点、300章、944块 | 不应全部进入首开关键路径 |
| 新分组已落地 | `groupPlanner.ts` 默认每组≤64段、128k上下文假设，组输出上限8000 tokens | 减少请求数不等于降低单请求延迟；超大输入与较窄输出还可能压低细节召回 |
| 抽取串行 | `coordinator.executeRun` 每轮只取 `executable[0]` 并 await 完整结果 | 总时长累加；可以优化，但不解决全书先行的规模问题 |
| 手机能力未贯通 | `sourceImport.ts` 创建group run没有传入profile的模型budget | 默认128k不是所有端点的已验证容量，必须修正 |
| 历史计时不足 | `.tmp/full-build/metrics.jsonl` 当前只记录导入916ms、创建15组，未记录逐组完成与最终映射 | 两小时是用户观测；本次无法从现存日志拆出每阶段占比，不能编造“多少时间花在推理” |
| 桌面容量探针失真风险 | `scripts/full-novel-build.cjs` 对重复文本只检查HTTP200，未验证marker回答或实际输入token | 请求被接受不证明长文完整利用，更不证明抽取质量或最佳批长 |
| App三书终点另有断链 | `buildRunner.ts` 仅调用runExtraction；`sourceImport.runExtraction` 仅executeRun；其完成只标世界ready | 必须补接实际编译/发布；不能“抽取完成”就显示“世界可玩” |
| 战役依赖固定包 | `createCampaign.ts` 要求published，并锁packageRevision；`session.ts` 基于锁定revision读条目 | 渐进扩充不是简单更新世界包，需设计兼容的增量绑定 |

额外可靠性问题：协调者默认租约120s，但mobile单请求timeout300s，桌面探针600s，当前续租发生于单元之间。长请求期间存在租约到期被另一个入口接管的风险，应以独立续租、原子领取、owner区分及fencing覆盖解决。不要用增大并发放大此问题。

本轮没有重跑两小时全量任务，也不使用旧全文脚本：该脚本会删除指定工作目录中的原数据库，不适合诊断已有成果。

## 3. 路线比较与选择

| 路线 | 首开成本 | 风险 / 适用位置 | 结论 |
|---|---|---|---|
| 全量抽取提高到2–4并发 | 仍与全书大小成正比 | 端点限流、token吞吐上限、长尾、成本依旧 | 仅用于可选全量整理 |
| 整本或巨组一次性生成三书 | 少请求但大输入输出 | 容量、召回、输出截断、校验和失败重试成本 | 不作为默认 |
| 全书先摘要再映射 | 仍要读完整本，另加阶段 | 摘要损失原文细节、证据难追踪 | 非首开必需，可做后续局部摘要 |
| 远端预制/共享世界包 | 缓存命中后快 | 服务、权限、小说版本、版权与模型来源管理 | 后续选择，不做本次前置服务 |
| **本地索引+开局包+按需扩充** | **由开局预算控制，脱离全书LLM扫描量** | 必须治理按需延迟、原著一致性、版本与秘密 | **采用** |

研究参考：Microsoft的LazyGraphRAG讨论了不预先用LLM总结全部源文、将处理推迟到查询时的路径。这支持本次减少前置模型工作的方向，但其研究成绩不能当成Shine-TRPG的速度保证，也不要求本项目引入GraphRAG框架或Azure服务。[Microsoft Research](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)

## 4. 首开关键路径：固定预算，先有可玩的场景

### 4.1 本地导入与索引

复用已有流式源、分章、shard与码点范围，不退回全文base64。并行于UI展示目录、角色选择说明和准备状态。

第一版检索不需要对整书调用embedding模型。建立可分页的中文倒排检索：人名/别名精确匹配、中文二元词项、章/段邻接、最近章节加权。优先验证现有SQLite是否支持需要的FTS模块与中文切词；不假定unicode61会自动切好中文。没有合适FTS时用自有posting表及有界ranker，批量写入、增量构建。

索引允许未全部完成时只开放已具备索引与正文的开局范围；源完整性校验仍需完成规定的激活门禁。若以后要边导入边玩，另设明确的分片激活协议，不能直接绕过现有SourceManifest完整性。

### 4.2 定义开局范围

- 默认从小说起点开局，选择开篇相邻章节，有界正文初始上限 **8k–12k码点**，并受实际token预算二次限制。这是调参起点，不是模型容量声明。
- 仅生成当前开局所需：少量人物/地点、即时处境、可见关系、必要原著限制及一个可操作的遭遇/任务入口。
- 如用户选中较后章节或未在已处理范围内的人物，先针对其锚点准备一个同样有界的开局，不触发全书精读，也不假装已具备该人物全生涯知识。
- 任意原著角色开局的资格由已验证资料决定；尚无安全模板则提示需要补齐或提供原创角色，不给模型编造原著角色卡。

### 4.3 开局模型请求与本地编译

目标 **1个主要模型请求，最多1个有界修复请求**（物理请求计数包括Provider自动重试，不能只统计逻辑调用）。请求输出受约束的OpeningDossier：关键实体、逐字引文事实、地点/状态、少量开局提案、缺失项。

规则书的基础机制、技能、常规物品、通用NPC参数来自已审查的本地模板与固定ruleset；不让LLM为每本小说重写同一套基础规则。小说特有能力只生成提案，未校验前不进入权威数值。

本地`compileOpeningPackage`直接将Dossier与固定模板编译为完整可执行的**开局范围包**，复用现有schema、引用、证据和发布校验，减少“抽取后再用另一个大请求映射同一批信息”的重复模型工作。

不得把现有全量builder只喂前几章、随后沿用“全书构建成功”文案。新契约明确：

```text
buildMode = progressive
scope = opening / region / complete
sourceCoverage = 精确码点范围与已验证内容标识
playability = ready / preparing / blocked
completeness = partial / complete
```

`playability=ready`表示当前作用范围引用完整、规则可执行、必需资料通过；不表示原著已全读。此契约需要有版本的manifest/迁移，覆盖所有导入导出和哈希，不只是validationJson里的展示字段。

## 5. 游玩时按需补齐，不能把两小时转嫁成每回合等待

### 5.1 检索触发与优先级

1. **P0 当前动作缺少必需资料**：当前地点、目标NPC、交互物品、资格判断必需限制。先本地缓存/检索，必要时有限一次扩充；缺关键证据就明确资料不足，不让模型猜权威状态。
2. **P1 近未来预取**：玩家阅读或处理普通行动时，预取下一地点、相邻章节、当前NPC相关段落。最多一个后台任务，前台网络请求拥有优先级；遇低带宽/限流立即暂停预取。
3. **P2 玩家主动查书**：命中条目即显示；未构建但有检索范围则提供“整理相关资料”，任务合并去重，避免翻页引起无上限生成。
4. **P3 全书精编**：默认不自动运行。仅用户主动选“完整整理三宝书”时运行原全量流程，说明预计成本。

默认后台只做有界局部预取，不能换一个名字继续偷偷读完整本书。

### 5.2 每次请求预算

- 默认取top-k相关段落并补相邻段，去重后总源文上限约4k–8k码点；不是把命中的整章无限加入。
- 优先实体/别名/地点精确检索，结合章节邻接；必要时少量语义索引按热点渐进建立，不增加全书embedding前置。
- Query plan主要来自当前branch state、actor/location/item ID与用户行动，本地可推导时不新增一个“LLM想搜索词”的回合。
- 主持Planner/Narrator照旧使用固定游戏请求预算；有必要的资料检索在冻结合同前完成。扩充请求单独受整个动作物理请求上限约束，不能用新role绕过原请求预算。
- 并发调用同一范围复用同一job；缓存key含sourceHash、范围、prompt/schema/model版本及抽取语义。
- 已验证资料可跨相同源的战役复用；可见性、当前状态与知识不能跨branch共享。

### 5.3 不篡改权威状态与原著

- 原文是证据库；模型补充不是原文真相。explicit必须能回放引文；推断、规则映射、设计补全分别标注。
- 小说里未提到不等于不存在；top-k没有结果不等于否定某个规则。无法确认的关键限制进入待补齐，不冒称全书无禁忌。
- 新资料不能覆盖玩家已经改变的世界。区分source canon、开局锚点快照和branch事件派生状态；NPC在当前战役死亡后，不能因检索到后面原著出场而复活。
- 全局伏笔、远距离关联、任意后期角色和复杂倒叙可能比全书精编模式更弱，需明确暴露该能力边界；用关联段扩展与后台近域补齐降低风险，不宣称质量自动等价。
- 新发现与已绑定规则冲突：停止影响权威结算的扩充、建立review记录；已经发生的骰点/事件不重写。事后只能做显式迁移或叙事解释，不能静默更改历史。

## 6. 增量三宝书与版本锁：本次最大工程边界

现有战役锁定单个packageRevision，不能直接改为“永远读取最新包”，也不能在原revision中追加条目。

采用 **不可变基础包 + 不可变增量包 + 战役绑定清单**：

- BasePackage：开局机制与初始条目，hash固定。
- ExpansionPackage：同一源版本、明确作用范围、新条目及出处；不得原地改既有包。
- ContentBindings：某个branch可用的base/expansion revision+hash集合，与stateVersion原子绑定。
- 回合开始先固定ContentBindings；冻结合同之后即使后台扩充完成，本回合也仍使用旧集合。只有下个安全边界才能接纳。
- 扩充全局编译可以完成，但对当前branch的绑定要经过幂等业务事件。分叉继承分叉时的绑定；rewind恢复当时集合；导出必须包含所需增量包或可验证依赖，缺包干净拒绝。
- 已有角色技能/HP/物品定义和用过的规则不得因增量自动升级；普通新增百科条目与数值规则变更走不同门禁。结构冲突需要review，不允许后到条目覆盖。
- 旧格式存档当作仅含base的绑定集合，保持读取；新格式明确版本，不把新字段塞进旧格式后声称完全兼容。

此变更必须贯通：`createCampaign`、`session`的loadPackageEntries、`v2Compile`、冻结合同依赖、turn commit、snapshot、fork/rewind、worldPackageArchive、saveFile、玩家投影和三书阅读器。仅改Library和publish门禁不能交付。

分两步降低风险：先上线“不可变开局包、限定开局范围可玩”；然后完整交付增量绑定后开放跨范围自由探索。中间版本必须标注范围，不宣传为已实现随探索补齐。

## 7. 秘密与时间

- 检索器接收明确的branch、角色知识、锚点与源范围策略。不能检索全书后直接把后期秘密塞给玩家或Planner。
- 阅读序号不等同世界时间；倒叙/预叙的事实若无法安全定位，标未解析时间，不直接当作“现在已经发生”。
- 后台可以处理尚未公开的资料，但产物仍为GM/undiscovered，玩家投影另行过滤；检索索引中出现一个名字不授予知识。
- NPC内心、隐藏身份、未来事件、物品秘密属性做专项对抗测试。原始检索片段是否可以交给Planner也要检查，不能只在最终UI遮盖。

## 8. 性能目标与实验

下列是拟定上线目标，尚未实测达到：

| 指标 | 新门槛 |
|---|---|
| 导入到目录/准备界面 | 用户有立即反馈；本地导入耗时独立记录 |
| 《白篱梦》首次可玩 | 目标中位数≤60s，P95≤120s；含本地准备、真实模型、编译、发布、开局 |
| 首开物理模型请求 | 正常1次；修复/重试总上限2次，达到上限明确可恢复失败 |
| 全书LLM阅读量 | 首开不读取全书；约8k–12k码点源文只是输入预算，非保证用时 |
| 普通已覆盖行动 | 不因资料扩充新增强制网络请求 |
| 按需命中缓存 | 本地查询P95目标≤200ms |
| 按需未命中 | 有准备状态、可取消和恢复；记录P50/P95，若频繁阻塞则策略验收不通过 |
| 前10回合体验 | 额外资料请求次数、累计等待、重复调用数必须独立计量，不能只看首开 |
| 全量整理 | 独立可选任务，不能抢占前台游玩请求，不影响开局完成定义 |

若GLM实际单个小请求仍显著超过目标，先用测量比较模型/输出schema/请求体，不关闭用户已确认的推理政策，不把加载文案变化当作速度提升。

必须做同素材同端点A/B：旧全量模式、受控并发全量模式、渐进开局。全量过慢可使用已有完整计时，但证据缺失时明确未测；不要为证明新模式随意再跑高成本两小时任务。

## 9. 本轮实验与首个施工门禁

本轮在收束为文档交付前运行过一次临时有界探针：当前真实抽取器与Provider、最多12k码点、少量开局资料、保留推理。**实际一次物理请求90秒超时，没有取得有效抽取结果。** 临时脚本已移除，未修改产品代码、数据库、战役或发布包。

因此新架构能确定减少首开的工作量，但不能据此证明当前模型端点能达到一分钟开局。实验范围及施工Agent复现步骤见 [有界开局实验记录](reviews/closeout/PROGRESSIVE_OPENING_PROBE.md)。

G0必须先对端点做有界诊断矩阵：

1. 小型非小说JSON请求与1k、4k、8k–12k原文请求逐级测量；每档限定尝试次数、总deadline和费用，不做无限容量探测。
2. 分开记录请求排队/建连/收到响应头/首个可用token/完整响应、实际usage与推理token（端点提供时），核验运行的是用户配置的真实模型与路由。
3. 比较“开局少量字段”与现有通用实体/事实/事件大schema；若任务需要过多生成，缩小首开职责和输出结构，不自动关闭推理。
4. 在已有可用配置范围比较第二模型；没有实际可用模型就明确缺项，不假设换模型一定更快。
5. 若小请求也慢，优先处理网络/网关/模型服务；若只有长请求慢，收紧输入和输出。HTTP200、简单marker回显不能证明长文理解质量。
6. 只有测得完整OpeningDossier并通过引用和可玩编译校验，才能确定产品默认预算；若端点无法满足TTFP，报告阻断项与可选模型配置，不能用“进入创建角色页面”冒充首次可玩。

## 10. 实施顺序

| 阶段 | 交付内容 | 出口 |
|---|---|---|
| G0 可观测性及可靠性 | 每次物理请求的阶段/输入输出/排队/网络/重试；修容量配置与长请求租约；修App抽取→编译断链 | 失败不假完成，完整数据可追踪 |
| G1 开局编译纵向切片 | OpeningDossier、确定性模板编译、范围包manifest、发布/开局资格、Library文案 | 真实小说→开局包→原创/有证据原著角色→首回合；1–2请求预算 |
| G2 原文检索 | 中文词项/别名、邻接、范围/时间/权限过滤、top-k预算、索引续建 | 已标注场景查询，关键证据召回与秘密隔离；低端Android性能 |
| G3 按需构建与预取 | P0/P1队列、去重、缓存、取消、后台预算、前台优先 | 连续10回合不被补书频繁打断；未命中不编造 |
| G4 增量绑定全链路 | base+expansion+bindings、snapshot/save/fork/rewind、冲突隔离 | 固定合同、回退、重启、存档导出导入全程一致 |
| G5 三书产品与设备验收 | 当前可用条目、未整理/未发现区分、阅读入口、可选全量任务 | Android Release端上TTFP和10/100回合指标，旧数据升级 |
