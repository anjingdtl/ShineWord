## 3. 完成合同与计数口径

### 3.1 必须同时完成

1. J1/J2/J3 各至少 20 个有效决定，J4-A/B 各至少 10，合计至少 80。J1 继承 5，尚需新决定 75；短冒烟可复用到这些配额中。
2. 按已批准 C-2：J1 续 15 中 Android UI 至少 10；J4 一路 10 由 Android UI 完成。UI 最少 20 是这 80 的子集。J1 余下 15 优先全部走 UI，不能事后再补一轮重复旅程。
3. 至少两项后果分别证明：排程 → 中间至少两个有效决定 → 触发 → 后续人物、办法、资源、条件或代价实际受影响。记录四段具体 turn/event/状态证据。
4. 三个自动计划及对应三条实际旅程分别完成六维评分，每维至少 3；世界冲突、重大泄漏、强行回滚合法结果一票否决。计划侧评分不能代替旅程评分。
5. 至少一场自然达到规则可验证的结局；短篇提前结束的合法结果保留，不能延长骰点、加空任务或复活已结束节点凑 20。新增样本独立journeyId、独立计数，不能拼到已结束Jx；若替换正式样本，替换旅程自身须达20，重新核算预算、继承与渠道，不能自动承接J1历史5。
6. 完成 A01–A40、最终身份和受影响复验、Android 功能矩阵、匹配 10+10 性能和全物理请求对账。
7. 独立试玩者或用户能够描述当前目标、自己改变了什么和下一步期待。实施者内容评分不替代试玩反馈。

只有上述全部闭合才称“第九阶段彻底完成”。“工程全绿”“技术验收通过但体验未验”“有诚实交接”可以分别报告，均不能代替完整收尾。

### 3.2 有效决定的判定

每次提交先列审计候选，再按当时可见信息和真实后续影响确认。证据至少包含 `journeyId / branchId / turnId / channel / executionIdentity / beforeVersion / afterVersion / methodId / outcomeGrade / businessEvents / authorityDiff / semanticVerdict / exclusionReason`。

- 状态变化须与目标、方法、成本或后续机会有关；无意义的 counter 重复增长不算。
- 合法失败可以继续游戏，但没有可核实影响的失败不能自动计作有效决定；也不能把失败本身当作代码缺陷。
- 管理采用、轮询、NPC 自动步、同一未提交回合重试、纯文案回显、无效果 fallback 不计。
- 后果间隔按**已确认有效决定**计算，不按版本号、正文数量或候选总数计算。
- 连续三次failure/severe_failure即暂停驱动诊断，已产生的合法有效变化保留；非失败档连续两次无持久变化也暂停。当前没有战役办法时，立即停止付费动作，处理内容供给。
- 不新加“每阶段必须 3 个决定”的生产硬门，也不禁止一次行动提前完成阶段。审查的是可选择、有代价、有后续影响的机会，不能保证固定故事长度。

旧表 `74×2+18+5=171` 使用了未批准的第六个继承决定。当前应为 `75×2=150` 个 Planner/Narrator 请求；按旧额外假设估算为 `150+18+5=173`。**150 是当前双请求回合模式的请求下界，173 只是修正后的估算，不是全通成本承诺。**

## 6. 执行顺序、责任与退出条件
